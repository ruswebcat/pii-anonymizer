# Техническое задание: прокси обезличивания персональных данных (LLM-guard)

**Проект:** контур ИИ-агента оператора, обрабатывающего персональные данные клиентов.
**Версия документа:** 1.0.
**Заказчик:** оператор (владелец данных и решений о режимах обработки).
**Юридическая рамка:** 152-ФЗ ст. 3 п. 9 (обезличивание), ст. 3 п. 1 (понятие ПД), ст. 6 ч. 1 п. 9,
ст. 12 (трансграничная передача), ст. 18 ч. 5 (локализация), ст. 18.1 ч. 5 (оценка вреда);
приказ Роскомнадзора от 19.06.2025 № 140 — метод № 1 «введение идентификаторов» (замена значений
ПД идентификаторами со справочником соответствия); КоАП 13.11; УК ст. 272.1.

---

## 1. Назначение

Прокси перехватывает весь трафик агента к языковым моделям и **на входе заменяет персональные
данные на обезличенные идентификаторы (коды)**, а на выходе восстанавливает их по настройке — для
каналов, которые оператор считает своими, и в локальных файлах; каналы вне контура значения не
получают никогда.

Цель: агент продолжает работать с клиентскими данными (расчёты, списки обзвона, разборы анкет),
но **во внешнюю модель не уходит ни одно значение, позволяющее определить субъекта**.

Реализует метод № 1 приказа РКН № 140 (введение идентификаторов + справочник соответствия).
Прокси — не «косметика»: после него обязателен **тест на обратимую идентификацию** (раздел 10).

---

## 2. Границы и место в архитектуре

```
[Пользователь]
   доверенный мессенджер (внутри контура) / внешний мессенджер
        │
   агент (хост контура)
   ├── инструменты: terminal/file/code_execution → API системы учёта клиентов
   │
   └── LLM-трафик ──► [ПРОКСИ ОБЕЗЛИЧИВАНИЯ 127.0.0.1:8791]  (хост контура)
                          │  вход: токенизация + валидатор
                          │  выход: детокенизация (по каналу)
                          ├──► маршрут основного поставщика модели
                          └──► маршрут поставщика изображений и медиа
```

Размещение: тот же хост контура, отдельный systemd-юнит, порт **только на loopback**.

Ключи поставщиков переносятся в прокси. Агент получает фиктивный ключ — прокси становится
**единственной точкой выхода LLM-трафика**.

## 3. Функциональные требования

| ID | Требование |
|---|---|
| F-1 | Прокси OpenAI-совместим: принимает `POST /{route}/v1/chat/completions`, `/v1/embeddings`, `/v1/models`; таблица маршрутов задаётся настройками |
| F-2 | Токенизация выполняется по **всему** телу запроса: `system`, вся история `messages`, `tool`/`function` результаты, аргументы предыдущих `tool_calls` |
| F-3 | Коды **детерминированные**: одинаковое значение → одинаковый код (обязательно: иначе ломается кэш подсказок поставщика и растёт стоимость запросов) |
| F-4 | Формат идентификатора: `zP482193` — префикс `z`, буква класса (P — ФИО, T — телефон, E — e-mail, D — дата рождения, A — адрес, I — документы, C — клиентские номера), восемь знаков base32 (40 бит), без обрамления. Идентификатор не содержит исходных данных и не перебирается. Прежние форматы записи продолжают распознаваться |
| F-5 | Детокенизация: (а) **аргументы `tool_calls` перед исполнением** — иначе агент не сможет обращаться к системе учёта; (б) финальный текст — **только для доверенных каналов**. Канал вне контура не детокенизируется, и указать его доверенным нельзя |
| F-6 | Ответ внешней модели возвращается постранично без задержки (SSE-совместимость) с буфером, чтобы код не разрезался между кадрами |
| F-7 | Кэш токенизации для уже обработанных блоков истории (LRU, ключ — sha256 блока), чтобы не сканировать сотни килобайт истории на каждом запросе |
| F-8 | Политика изображений: по умолчанию изображение проходит, а ответ несёт напоминание о том, что содержимое изображений не обезличивается; строгий режим отказа — переключатель |
| F-9 | Пасс-тру через прокси неподдерживаемых путей и заголовков; корректный перенос `stream`, `tools`, `response_format`, `temperature` и пр. |
| F-10 | Health-эндпоинт `GET /healthz` (локально) + запись статуса в журнал |

## 4. Классы сущностей и правила детекции

Порядок применения: **словарь → правила → эвристики**. Словарь (значения из карточек клиентов,
телефоны, номера договоров) выгружается из системы учёта локальным скриптом и обновляется по
расписанию, без обращения к языковой модели.

| Класс | Что распознаём | Ключ детекции |
|---|---|---|
| P — ФИО | Полное ФИО, фамилия+инициалы, отдельная фамилия в падеже | Словарь значений + шаблон «Слово с заглавной + Слово(-в/-ев/-ин/-ова/-ская/-ий)» + окончания падежей (`-у`, `-ым`, `-ой`, `-ых`) |
| T — телефон | `79xxxxxxxxx`, `89xxxxxxxxx`, с `+7`, пробелами, скобками, дефисами | Нормализация к 11 цифрам, проверка префикса 7/8 |
| E — e-mail | Любой e-mail | RFC-подобная регулярка |
| D — дата рождения | `дд.мм.гггг`, `«12 марта 1985 г.р.»` | Регулярка + контекст («г.р.», «дата рождения»). Год допускается оставлять открытым (решение оператора) |
| A — адрес | Улица/дом/квартира | Регулярка улиц (ул., пр-т, б-р, ш., д., кв.) |
| I — документы | СНИЛС, паспорт, ИНН физлица, ОГРН, счёт | Форматные шаблоны + контрольная сумма там, где она есть |
| C — клиентские номера | `client_id`, номер договора/карты/анкеты, номер заявки | Словарь ключей + контекст (`client_id`, `№ договора`) |
| O — прочее | ФИО в свободном тексте заметок, инициалы | Эвристики + опциональный NER (раздел 12) |

**Обязательно к учёту:** детекция должна работать и по **выгрузкам** (CSV/XLSX, читаемым агентом
как текст). Заголовки колонок (`ФИО`, `Телефон`) — маркер: значения в этих столбцах токенизировать
безусловно.

**Своя лексика оператора** (бренд, филиалы, тарифы, город, свои адреса, телефоны ресепции,
название системы учёта) в код не зашивается: она задаётся настройками и никогда не заменяется.

## 5. Справочник соответствия (по приказу № 140 — декомпозиция)

| ID | Требование |
|---|---|
| S-1 | Справочник `pii_map.db` (SQLite, локально, права 0600): `token, cls, value_enc, created_at, last_used_at` |
| S-2 | Значения хранятся **зашифрованными** (Fernet, библиотека `cryptography`). Ключ — отдельный файл 0600 вне каталога резервных копий |
| S-3 | Ключ шифрования ≠ ключ генерации кодов. Код = `base32(HMAC-SHA256(token_key, cls \|\| normalized_value))` |
| S-4 | Справочник хранится отдельно от рабочих массивов ПД (декомпозиция), доступ — только у процесса прокси |
| S-5 | TTL записей — 90 дней (настраиваемо), автоочистка по расписанию |
| S-6 | Справочник **не** попадает в облачные резервные копии и в git |

## 6. Журналирование

| ID | Требование |
|---|---|
| L-1 | Тела запросов/ответов нигде не логируются (ни в файл, ни в stdout) |
| L-2 | Журнал обезличивания: `ts, session_id, direction, класс, количество, действие (tokenized/detokenized/blocked)` — **без значений**. Это документ для регулятора |
| L-3 | Ошибки санитизируются: исключение сообщается без фрагментов полезной нагрузки |
| L-4 | Метрики: p50/p95 задержки, число кодов на запрос, доля блокировок; алерт при блокировке — в служебный канал |
| L-5 | Журнал хранится локально; срок хранения определяет оператор |

## 7. Безопасность и отказоустойчивость

| ID | Требование |
|---|---|
| N-1 | Слушает только loopback; наружу не публикуется |
| N-2 | **Fail-closed:** при недоступности справочника, ошибке токенизации или срабатывании валидатора запрос к модели **не отправляется**; агент получает ошибку и работает в деградированном режиме (только локальные скрипты) |
| N-3 | Валидатор исходящего запроса (после токенизации): ищет остаточные маркеры — цифровые последовательности, `@`, словарные значения без кода, даты в формате `дд.мм.гггг`. Нашёл → починка вторым проходом, при неудаче блок + запись в журнал + алерт |
| N-4 | Ограничение прямого выхода: firewall запрещает процессу агента прямое соединение с поставщиками моделей — обойти прокси технически невозможно. Включается только после того, как прокси проверен на живом контуре |
| N-5 | Зависимости — только stdlib Python 3.11 плюс `cryptography` и `pymorphy3`. Никаких pip-установок в боевом контуре |
| N-6 | systemd-юнит, `Restart=always`, автозапуск, лимит памяти |
| N-7 | Резервный канал: если прокси отключён, весь LLM-трафик отключается целиком — режим «только скрипты» (переключатель) |

## 8. Нефункциональные требования

| ID | Требование |
|---|---|
| P-1 | RSS ≤ 150 МБ, CPU ≤ 1 ядро в пике |
| P-2 | Задержка: +≤ 50 мс на 100 КБ текста (словарь+правила); +≤ 300 мс при включённом NER |
| P-3 | Совместимость с SSE-стримингом клиента |
| P-4 | Не ломать кэш подсказок поставщика: детерминированные коды + стабильный порядок замен |
| P-5 | Установка/обновление без остановки агента (юнит рестартует за < 1 с) |

## 9. Что прокси НЕ решает (границы применимости)

Обязательный раздел: эти риски закрываются другими мерами.

1. **Квазиидентификаторы.** Комбинация «клуб + дата + тип карты + сумма» может быть уникальной —
   субъект определяется без ФИО. Требуется отдельный слой: порог k ≥ 5 и запрет редких комбинаций.
2. **Внешний мессенджер как канал.** Сама переписка в зарубежном мессенджере — трансграничная
   передача. Прокси не делает такой канал безопасным; операции с ПД должны идти только на
   доверенных каналах.
3. **Обратный возврат.** Если восстановленные данные возвращаются агенту и приводят к решению о
   конкретном человеке (кому звонить), это снова обработка ПД конкретного субъекта;
   «обезличенность в транзите» регулятор оценит как маскировку.
4. **Хранение у провайдера.** Внешние поставщики хранят ввод на своих серверах и по умолчанию
   могут использовать его для обучения (opt-out есть). Для обезличенных данных допустимо, для
   ПД — нет.
5. **Изображения.** Не токенизируются: политика — не отправлять либо распознавать локально.

## 10. Тест на обратимую идентификацию (обязательный шаг приказа № 140)

Методика приёмки:
1. Выборка 100 записей клиентов (разных клубов, длительностей, источников).
2. Прогон через прокси, сохранение обезличенного результата.
3. Три попытки реидентификации:
   - две независимые проверки «глазами» (исполнители, не участвовавшие в разработке);
   - автопоиск уникальных комбинаций признаков (флаг при k < 5);
   - кросс-сопоставление с открытыми источниками по оставшимся признакам.
4. **Критерий приёмки: 0 успешных реидентификаций.** Результат оформляется актом (приложение к
   регламенту обезличивания), см. `docs/ACT.md`.

## 12. Конфигурация агента (после внедрения)

```yaml
model:
  default: <модель>
  provider: <поставщик>
  base_url: http://127.0.0.1:8791/<маршрут>/v1     # вместо адреса поставщика напрямую
auxiliary:
  vision:
    provider: custom
    model: <модель изображений>
    base_url: http://127.0.0.1:8791/<маршрут>/v1
```

Ключи поставщиков переносятся в окружение прокси; в профиле агента остаются фиктивные значения.

Своя лексика оператора (бренд, филиалы, тарифы, клубы, город, свои адреса и номера ресепции)
задаётся разделом `own_vocabulary` и переменными `PII_PROXY_OWN_*` — раздел описан в
`config.example.yaml`. Добавить туда своё название тарифа или клуба **достаточно**: служба не
станет считать его данными клиента, а сторож публичной сборки
(`tests/test_no_real_pii_in_repo.py`) следит только за отличительными названиями самой сборки (в
любом регистре) и за общеупотребительными словами — лишь как за именем собственным.

## 13. Критерии приёмки

1. В обезличенном трафике к модели нет ни одного ФИО, телефона, e-mail, номера договора —
   проверено валидатором N-3 и ручной выборкой запросов.
2. Агент сохраняет работоспособность: расчёты, списки обзвона, отчёты — выполняются штатно.
3. Детерминированность кодов: повторный запрос с той же историей даёт тот же набор кодов; расход
   кэша подсказок не деградировал.
4. Fail-closed подтверждён тестом: остановка прокси → запросы к модели блокируются, операции с ПД
   не выполняются.
5. Прямой выход к поставщику с хоста агента запрещён (тест с `curl`).
6. Акт теста на обратимую идентификацию (раздел 10) — 0 реидентификаций.

## 14. Решения оператора (по открытым вопросам)

1. **Детокенизация финального текста — по настройке `detok_channels`** (список каналов либо признак
   «любой канал»; умолчание публичной сборки — любой канал, решение владельца 25.09.2026). Оператору,
   которому приватность важнее удобства, список следует сузить до доверенных каналов (см.
   `docs/PRIVACY.md`, раздел 3). Канал вне контура коды не восстанавливает ни при каком значении
   настройки: текст остаётся в кодах, факт фиксируется как `channel_blocked`.
2. **Классы D и A:** год рождения остаётся открытым, день и месяц токенизируются; адрес
   токенизируется полностью.
3. **NER — включаем.** Обязательна ленивая загрузка, чтобы не занимать память при простое.
4. **Firewall-запрет прямого выхода (N-4) — отдельным шагом после приёмки.** Порядок и цена —
   `docs/OPERATIONS.md`.
5. **TTL справочника соответствия — 90 дней.** Ответственный за журнал обезличивания
   определяется регламентом (роль, а не человек).
6. **Своя лексика — настройка, а не код** (решение владельца 25.09.2026). Если в организации есть
   тариф, клуб, услуга, филиал или город, которых нет в примерах, их добавляют в
   `own_vocabulary.terms` (`PII_PROXY_OWN_TERMS`). Сторож `tests/test_no_real_pii_in_repo.py`
   ловит только отличительные названия самой публичной сборки (в любом регистре) и
   общеупотребительные слова — лишь как имя собственное: с заглавной буквы или в связке
   «тариф …», «клуб …». Обычное слово в середине фразы находкой не считается, поэтому
   прозаические употребления в документах остаются естественными, а сборка пригодна для другой
   организации с таким же названием тарифа.

> **Формат кода.** Действующий формат — `zP482193` (префикс, буква класса, восемь знаков base32,
> без обрамления). Экзотические скобки `⟦…⟧` модель при копировании искажала: в замере она
> вернула код **без** обрамления, из-за чего восстановление молча не срабатывало. Прежние
> форматы записи продолжают распознаваться (совместимость со справочником), код без обрамления —
> тоже.

## Политика изображений

Изображения **не блокируются**. Правило «запрос с изображением — отказ» было несогласованным по
последствиям: одного скриншота в истории сессии достаточно, чтобы все последующие обращения к
модели перестали проходить, а распознавание изображений через прокси становилось невозможным в
принципе. Защита, которая ломает саму возможность работы, — неверная защита.

Принято: запрос с изображением проходит, а в ответ добавляется напоминание:

> В запросе были изображения. Они передаются без обезличивания: если на них есть персональные
> данные клиентов, это нарушение политики обработки персональных данных.

Напоминание фиксируется в журнале событием `image_notice`. Строгий режим (отказ) сохранён как
возможность: `PII_PROXY_IMAGE_POLICY=block`; по умолчанию — `allow`.

**Что это значит по существу.** Изображения — единственный канал, который обезличивание не
закрывает: содержимое картинки не превращается в идентификатор. Ответственность за то, чтобы на
изображении не было персональных данных клиентов, остаётся на том, кто его отправляет, и теперь
она проговаривается в чате, а не нарушается молча.
