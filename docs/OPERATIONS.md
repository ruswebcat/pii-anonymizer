# Эксплуатация прокси обезличивания

Документ для того, кто дежурит на хосте контура: как поднять, как проверить, как править словарь, что
делать при отказе. Устройство и «почему так» — в `docs/ARCHITECTURE.md`, правовая рамка — в
`docs/PRIVACY.md`. Снимок чисел — 25.09.2026.

## 1. Где живёт служба

Прокси стоит на том же хосте контура, что и агент, слушает **только локальный интерфейс, порт 8791** и
поднимается как служба systemd. В репозитории два юнита, оба рабочие — выбирается режимом установки:

| Юнит | Режим | Каталоги состояния и логов | Конфигурация |
|---|---|---|---|
| `deploy/pii-proxy.service` | системный (`sudo`) | `/var/lib/pii-proxy`, `/var/log/pii-proxy` | `/etc/pii-proxy/pii-proxy.env` |
| `deploy/pii-proxy.user.service` | пользовательский | `~/.local/state/pii-proxy` (логи — в `log/` рядом) | `~/.config/pii-proxy/pii-proxy.env` |

Пользовательский режим применяется там, где `sudo` требует пароль; у него нет части директив
защиты (`ProtectSystem`, `ProtectHome`), которые недоступны в пользовательском менеджере, но
`NoNewPrivileges`, `PrivateTmp` и лимиты памяти на месте. Оба юнита имеют `StartLimitIntervalSec=60`
/ `StartLimitBurst=5`: ошибка настройки должна выглядеть как упавшая служба, а не как вечный цикл
перезапусков.

## 2. Установка и обновление

```bash
bash deploy/install.sh            # каталоги, ключи, файл окружения, юнит — без запуска
nano ~/.config/pii-proxy/pii-proxy.env    # вписать ключи поставщиков
bash deploy/install.sh --start    # поднять и проверить healthz
```

Установщик идемпотентен: существующие файлы ключей и файл окружения он не трогает. Ключи
создаются один раз и **никогда не меняются автоматически** — их смена делает прежние коды
неразрешимыми (см. раздел 11).

Обновление кода: `git pull` в каталоге репозитория и перезапуск юнита. Служба держит прежний код и
прежние файлы в памяти, поэтому после правки словаря и кода нужен перезапуск, иначе `healthz`
продолжит показывать старые числа.

## 3. Проверка живости и здоровья

```bash
curl -s http://localhost:8791/healthz | python3 -m json.tool
systemctl --user status pii-proxy.service      # системный режим: systemctl
journalctl --user -u pii-proxy -n 30           # системный режим: journalctl -u ...
```

`healthz` отдаёт числа и признаки по слоям; значений клиентов и путей в нём нет:

| Поле | Что показывает |
|---|---|
| `status` | `ok`, либо `degraded` со сбоем хранилища (`store_error`) |
| `bind`, `routes` | адрес и настроенные маршруты (`ds`, `nord`) |
| `store` | счётчики справочника: записей, кодов, истёкших по TTL |
| `dictionary` | размеры классов словаря и версия файла |
| `name_layer` | размеры открытого слоя (`counts.P`) |
| `ner` | доступность морфологии/NER и имя бэкенда |
| `validator`, `rarity` | включён ли заслон; порог k и режим |
| `incident_journal` | подключён ли журнал инцидентов и сколько записей не записано |
| `registry` | итог проверки инварианта «код значит одно значение» |
| `coherence` | режим заслона связности, индекс, счётчики |
| `provider_cache` | попадания в кэш поставщика по токенам и доля попаданий |
| `cache` | кэш блоков: попадания, промахи, устаревшие записи, размер в записях и байтах, вытеснения, предел объёма |

Кэш блоков хранит и блоки **с находками**, а не только чистые (решение 26.09.2026): без этого
история, где почти каждый блок несёт код, сканировалась заново на каждом запросе. Взамен запись
несёт ответственность за свои связи: ключ включает подпись справочника (путь, время правки,
размер, отпечаток ключа) и версию схемы, поэтому смена справочника гасит весь кэш сразу, а на
попадании каждый код обязан всё ещё разрешаться в то же значение — иначе запись считается
устаревшей (`stale`), отбрасывается и блок обезличивается заново.

Приёмка шага — это **поднятая служба с новым кодом**, а не зелёный тест: перезапуск, `is-active`
не `failed`, ответ `healthz`, и только потом вывод о результате.

## 4. Файлы состояния

| Файл | Что внутри | Права | Кто пишет |
|---|---|---|---|
| `token.key` | ключ кодов обезличивания | 0600 | только установщик |
| `dict.key` | ключ отпечатков словаря (отдельный от `token.key`) | 0600 | только установщик |
| `fernet.key` | ключ шифрования справочника соответствия | 0600 | только установщик |
| `pii_map.db` | справочник «код ↔ значение», шифрованный, TTL 90 дней | 0600 | служба |
| `pii_dict.json` | словарь частного слоя (schema 3, отпечатки значений и форм) | 0600 | выгрузка и тренер |
| `name_layer.json.gz` | открытый слой имён с происхождением и лицензиями в `meta` | 0600 | сборщик слоя |
| `pii_combos.json.gz` | индекс сочетаний ФИО (только отпечатки) | 0600 | сборщик сочетаний |
| `audit.jsonl` | журнал обезличивания: классы, действия, счётчики | 0600 | служба |
| `incidents/incidents-YYYY-WW.jsonl` | журнал инцидентов по неделям: промахи детектора без значений | 0600 | служба |

Словарь и слой имён подхватываются на первом же запросе — ручного перезапуска после их замены не
требуется (в журнале аудита видно `dictionary_reload`, а в `healthz` — новые числа). Ключи и файл
справочника подхватываются только перезапуском.

## 5. Настройки

Файл окружения — самый чувствительный артефакт на хосте: в нём ключи поставщиков. Он лежит вне
репозитория и в git не попадает. Значения по умолчанию перечислены в `deploy/pii-proxy.env.example`.

| Переменная | Смысл |
|---|---|
| `PII_PROXY_HOST`, `PII_PROXY_PORT` | привязка; не-loopback адрес отвергается на старте |
| `PII_PROXY_TOKEN_KEY_FILE`, `PII_PROXY_FERNET_KEY_FILE`, `PII_PROXY_DICT_KEY_FILE` | три ключа (см. раздел 4) |
| `PII_PROXY_MAP_DB`, `PII_PROXY_DICT`, `PII_PROXY_NAME_LAYER`, `PII_PROXY_NAME_COMBOS` | файлы состояния |
| `PII_PROXY_AUDIT_LOG`, `PII_PROXY_INCIDENT_LOG` | журналы |
| `PII_PROXY_TTL_DAYS`, `PII_PROXY_CACHE_SIZE` | срок жизни связок и предел кэша блоков по числу записей |
| `PII_PROXY_BLOCK_CACHE_MB`, `PII_PROXY_BLOCK_CACHE` | предел того же кэша по объёму (МБ, по умолчанию 64) и полный выключатель кэша блоков |
| `PII_PROXY_DETOK_CHANNELS` | где восстанавливать текст: список каналов (`mattermost,local`) либо `*` / пусто — любой канал (умолчание публичной сборки); канал вне контура отвергается |
| `PII_PROXY_TRUSTED_CLIENTS` | доверенные клиенты: `канал=способ:значение` через `;` (`cursor=ua:*cursor*;desk=key:sha256:…`) или JSON-перечень; способы `header`, `key`, `ua`. Шаблон пишется без номера версии. Пусто — опознавать некого |
| `PII_PROXY_UNKNOWN_CLIENT` | поведение для клиента, который не назвался ничем: `keep_codes` (умолчание, значения не восстанавливаются) или `restore` (прежнее поведение — решение по списку каналов) |
| `PII_PROXY_IMAGE_POLICY` | `allow` (по умолчанию, с напоминанием в ответе) или `block` |
| `PII_PROXY_STREAM_MODE` | `auto` (как просит клиент) или `json_only` |
| `PII_PROXY_NER_ENABLED`, `PII_PROXY_NER_BACKEND` | морфология/NER как слой распознавания |
| `PII_PROXY_RARITY_K`, `PII_PROXY_RARITY_ENFORCE` | порог k-анонимности для агрегатов |
| `PII_PROXY_COHERENCE_MODE` | `off` / `audit` / `enforce` для заслона связности |
| `PII_PROXY_DRY_RUN` | репетиция: считает, но не зовёт поставщика |
| `DEEPSEEK_API_KEY`, `NORDROUTER_API_KEY` | ключи поставщиков (их видит только прокси) |
| `PII_PROXY_ALERT_TELEGRAM_*`, `MATTERMOST_*` | куда отправлять алерты службы |

Замечание по разбору значений: systemd не поддерживает комментарии после значения, поэтому
`FLAG=true  # пояснение` приезжает целиком; разбор булевых значений обрезает комментарий и берёт
первое слово. Если флаг «не работает», сначала проверять файл, а не код.

### 5.1. Как подключить клиент к прокси: адрес модели — это адрес прокси

Прокси работает только тогда, когда клиент идёт **через него**. Для этого в клиенте нужно указать
**адрес прокси как адрес модели** (для OpenAI-совместимого клиента это `base_url`), а ключ
поставщика заменить заглушкой: настоящий ключ остаётся в файле окружения прокси (раздел 13). Пока
адрес модели указывает на поставщика напрямую, трафик идёт **мимо** прокси — и обезличивания, и
опознания клиента, и восстановления в таком запросе не будет вовсе.

Адрес строится как `http://127.0.0.1:8791/<маршрут>/<путь>`, где `<маршрут>` — имя из раздела
`routes` настроек (`ds`, `nord`), а `<путь>` клиент дописывает сам (`/v1/chat/completions`). Прокси
слушает только loopback, порт по умолчанию — **8791**.

| Клиент | Где задаётся адрес модели | Готовый вид |
|---|---|---|
| Claude Code (CLI) | `ANTHROPIC_BASE_URL` — переменной окружения или блоком `env` в `~/.claude/settings.json` | `ANTHROPIC_BASE_URL=http://127.0.0.1:8791/<маршрут>` |
| OpenAI Codex CLI | `~/.codex/config.toml`: `model_provider` и раздел `[model_providers.<имя>]` | `base_url = "http://127.0.0.1:8791/<маршрут>/v1"` |
| VS Code и его форки | настройками расширения, которое зовёт модель (`Continue`, `Cline`, провайдеры «OpenAI-compatible») | адрес прокси в поле `base_url`/`baseUrl` расширения |
| Cursor IDE | «Override OpenAI Base URL» в Cursor Settings → Models | **локальный адрес не годится** — почему и что делать, ниже |

```ini
# Claude Code: адрес прокси, ключ-заглушка вместо ключа поставщика, свой заголовок опознания
ANTHROPIC_BASE_URL=http://127.0.0.1:8791/<маршрут>
ANTHROPIC_AUTH_TOKEN=ЗАГЛУШКА-ВМЕСТО-КЛЮЧА-ПОСТАВЩИКА
ANTHROPIC_CUSTOM_HEADERS=X-PII-Channel: claude-code      # способ 1; ключ доступа — способ 2
```

```toml
# Codex CLI: ~/.codex/config.toml
model_provider = "proxy"
[model_providers.proxy]
base_url = "http://127.0.0.1:8791/<маршрут>/v1"
env_key = "PROXY_PLACEHOLDER_KEY"
http_headers = { "X-PII-Channel" = "codex" }   # способ 1 одним заголовком
```

**Два ограничения, о которых надо сказать прямо.**

1. **Cursor не может ходить на локальный адрес.** Запросы, которые Cursor отправляет на «Override
   OpenAI Base URL», уходят с его серверов, а не с машины оператора: локальный адрес для них — это
   loopback чужого сервера, и до прокси такой запрос не доходит. Что делать:
   - **оставить Cursor вне контура** (рекомендуется). Тогда запись `cursor` в `trusted_clients`
     нужна только на случай запросов, которые всё же придут к прокси (например, от расширений);
   - **задать адрес расширением внутри Cursor**: Cursor — оболочка VS Code, и расширение, которое
     само зовёт endpoint (`Continue`, `Cline` и подобные), работает из локального процесса — тогда
     адрес прокси доступен, а канал опознаётся по строке расширения, а не по строке IDE;
   - **выставлять прокси наружу туннелем — не рекомендуется**: служба обязана слушать только
     loopback, и адрес, доступный из сети, перестаёт быть границей контура — запрос к нему сможет
     поставить кто угодно. Это решение владельца, и оно резко расширяет поверхность.

2. **Прокси не переводит протоколы.** Он обезличивает текст и передаёт запрос поставщику маршрута
   тем же путём, поэтому маршрут обязан вести к поставщику, который говорит на том же языке, что
   клиент: Claude Code говорит на Anthropic Messages API, Codex CLI — на Responses API, обычные
   OpenAI-совместимые клиенты — на Chat Completions. Маршруты задаёт оператор (`routes`), и перед
   подключением клиента нужно убедиться, что маршрут ведёт туда, где этот язык понимают.

Признак успеха после подключения — не «запрос не упал», а **новые события в журнале прокси** и
`channel_source` в ответе (`header`, `key`, `user_agent`, `declared` или `none`): пока их нет,
клиент идёт мимо прокси.

### Как добавить новый клиент

Порядок один и тот же для Cursor, Claude Code, Codex и любого следующего приложения — выбирается
только способ опознания (подробнее о границах способов — `docs/ARCHITECTURE.md`, раздел 5, и
`docs/PRIVACY.md`, раздел 3).

1. **Понять, чем клиент может себя назвать.** Три способа по убыванию надёжности:

   | Способ | Кому подходит | Что нужно |
   |---|---|---|
   | Ключ доступа (`key`) | любому клиенту, которому можно задать заголовок `X-PII-Client-Key` | выдать клиенту ключ и записать его **отпечаток** |
   | Заголовок (`header`) | клиенту, который умеет ставить свой заголовок (`X-PII-Channel`) | имя канала в значении заголовка |
   | User-Agent (`ua`) | десктопным приложениям, которые заголовки не настраивают (обычный случай IDE) | фактическая строка User-Agent клиента |

2. **Отпечаток ключа** (способ `key`) считается локально, ключ при этом никуда не отправляется:

   ```bash
   install -d -m 0700 /etc/pii-proxy/client-keys
   head -c 32 /dev/urandom | base64 > /etc/pii-proxy/client-keys/cursor
   chmod 0600 /etc/pii-proxy/client-keys/cursor
   python3 -m src.client_identity "$(cat /etc/pii-proxy/client-keys/cursor)"
   # → sha256:<отпечаток> — его и вписывают в настройки, сам ключ остаётся в файле 0600
   ```

   Заголовок клиента: `X-PII-Client-Key: <содержимое файла>`. Ключ, которого нет в таблице,
   **не понижает** опознание до User-Agent: запрос считается неопознанным.

3. **Как снять фактическую строку User-Agent** (способ `ua`). Из документации клиента её брать
   нельзя: строку меняет каждое обновление, и шаблон с номером версии перестаёт совпадать молча.
   Порядок:

   ```bash
   python3 tools/ua_probe.py --once --dump /tmp/headers.txt
   # → Заглушка слушает http://127.0.0.1:8792 — укажите этот адрес в клиенте как адрес модели
   ```

   - указать в клиенте **адрес заглушки как адрес модели** (раздел 5.1) и повторить один запрос;
   - заглушка напечатает то, чем клиент себя назвал: `User-Agent`, `X-PII-Channel`, `x-app`,
     `originator`, а вместо значения ключа доступа — его отпечаток (сам ключ в отчёт не попадает);
   - снятые заголовки лягут в `/tmp/headers.txt` — файл читает прибор из шага 4;
   - шаблон писать **без номера версии**: `*cursor*`, `*claude-cli*`, `*codex*`, `*vscode*`,
     `*jetbrains*`. Заготовки по приложениям лежат в `config.example.yaml`, и там же сказано, где
     строка подтверждена, а где нет. Порядок записей — порядок приоритета: Cursor называет в своей
     строке и VS Code, поэтому запись Cursor ставится раньше.

4. **Проверить опознание прибором — до правки службы.** Прибор читает ту же таблицу настроек, что и
   служба, и показывает канал, источник, совпавший шаблон и решение для случая «клиент не назвался
   ничем»:

   ```bash
   python3 -m src.client_identity check --headers-file /tmp/headers.txt --config config.yaml
   #   канал:      cursor
   #   источник:   user_agent
   #   совпало:    *cursor*
   #   решение:    detokenize — канал назван, и он разрешён списком каналов
   ```

   Без файла годится строка: `python3 -m src.client_identity check "*строка*"`; `--json` даёт тот же
   отчёт машинным видом. Прибор предупреждает, если шаблон содержит номер версии, если
   предъявленный ключ не нашёлся в таблице (и напоминает, что опознание не понижается до
   User-Agent) и если канал не разрешён списком восстановления.

5. **Записать клиента в настройки** — файлом (`trusted_clients` в `config.example.yaml`) или
   переменной окружения:

   ```bash
   # компактно, для файла окружения systemd
   PII_PROXY_TRUSTED_CLIENTS="cursor=ua:*cursor*;codex=ua:*codex*;office=key:sha256:0000…"
   # по-другому тот же раздел задаётся перечнем записей в файле настроек (PII_PROXY_CONFIG)
   ```

   Канал обязан быть разрешён и в `detok_channels`: суженный список остаётся суженным, и опознание
   клиента его не расширяет. Канал внешнего мессенджера отвергается на старте.

6. **Подключить клиент и проверить, что работает, и что видно.** Адрес прокси как адрес модели —
   раздел 5.1; затем `systemctl restart pii-proxy` и `curl` к `healthz`: блок `trusted_clients`
   показывает каналы, счётчики способов и режим для неизвестного клиента; ответ прокси содержит
   `pii_proxy.channel_source` — по чему именно опознали клиента (`header`, `key`, `user_agent`,
   `declared` или `none`). Если `channel_source` равен `none`, а ожидался клиент — смотреть шаблон
   User-Agent и имя заголовка, а не код.

## 6. Порядок правки справочника (обязательный)

Любая правка боевого справочника идёт **одним путём** — иначе теряются настоящие значения (так
однажды выпало 12,9%). Порядок: собрать staged-файл → прогнать прибор → сделать бэкап живого →
заменить атомарно. Всё это делает `src/dict_write.py`, переставить шаги нельзя:

```bash
python3 - <<'PY'
from src import dict_write

# пути состояния: пользовательский режим либо /var/lib/pii-proxy (системный)
state = "/var/lib/pii-proxy"
live, key, layer = f"{state}/pii_dict.json", f"{state}/dict.key", f"{state}/name_layer.json.gz"

payload = dict_write.load_payload(live)
payload, stats = dict_write.remove_values(payload, open(key, "rb").read(), "P", ["Тест", "Гость"])
print(stats)
result = dict_write.apply(live, payload, key, layer_path=layer)
print(result.staged_path, result.applied, result.reason)
PY
```

Что важно знать про этот путь:

- **Провал проверки — не ошибка прогона, а решение «живой словарь не меняем»**: staged остаётся на
  диске, замены нет, бэкап не нужен.
- **Без бэкапа замены не делаем**: отказ бэкапа останавливает шаг.
- **Мерь до и после.** Прибор (`tools/quality_metrics.py`) сравнивает планки; замер «до» на реальной
  выборке — часть шага, а не формальность.
- **Шум словаря виден отдельно**: `tools/dict_noise_report.py` показывает, сколько служебной лексики
  сидит в классе «имена», не читая значений клиентов (сверка идёт по отпечаткам). Слова своей сети
  (тарифы, клубы, услуги) прибор берёт из настроек: `--config /etc/pii-proxy/config.yaml`, переменные
  `PII_PROXY_SERVICE_LEXICON` и `PII_PROXY_OWN_TERMS`. Без настроек он честно отчитывается по общим
  категориям, что замерять чужие тарифы ему нечем.

## 9. Журналы: что и где смотреть

```bash
tail -n 20 ~/.local/state/pii-proxy/log/audit.jsonl
ls -la ~/.local/state/pii-proxy/log/incidents/
journalctl --user -u pii-proxy -n 50
```

- **Журнал аудита** — классы, действия, счётчики, попадания в кэш. Значений и ключей в нём нет по
  построению (закрытая схема: новое значение поля отвергается).
- **Журнал инцидентов** — промахи детектора на живом трафике: время, канал, класс, действие,
  выданный код, правило-источник. Ни текстов запроса или ответа, ни значений, ни их фрагментов и
  хешей.
- **Алерты службы** уходят в чат и тему внешнего канала, заданные настройками; при пустых настройках —
  только в журнал.

Полезные срезы при разборе: доля запросов с ПД (`tools/pii_share_estimate.py`), цена кода в токенах
(`tools/token_cost_report.py`), непрерывность префикса кэша (`tools/cache_prefix_check.py`),
инвентарь реестра без значений (`tools/registry_integrity.py`).

## 10. Репетиция на реальных запросах

`PII_PROXY_DRY_RUN=true` прогоняет весь конвейер и **не вызывает поставщика**. Репетицию удобно
поднимать на другом порту рядом с боевой службой и прогонять по сохранённым реальным запросам
агента (`tools/dry_run_replay.py`). После репетиции записанные запросы, содержащие ПД, удаляются —
они не должны оставаться на диске.

## 11. Резервные копии и восстановление

Копировать нужно **три вещи вместе**: файл справочника (`pii_map.db`), ключи (`token.key`,
`fernet.key`, `dict.key`) и словарь со слоем (`pii_dict.json`, `name_layer.json.gz`,
`pii_combos.json.gz`). По отдельности они бесполезны: без ключа коды не разрешаются, без справочника
коды не значат ничего.

```bash
# снимок состояния одной командой
tar czf ~/backups/pii-proxy-state-$(date +%Y%m%d-%H%M).tar.gz \
  -C ~/.local/state pii-proxy
```

**Полный бэкап репозитория** (все ветки, все коммиты, включая удалённую историю разработки):

```bash
git bundle create ~/backups/pii-proxy-full-<штамп>.bundle --all
git bundle verify ~/backups/pii-proxy-full-<штамп>.bundle
```

Снимок, снятый при приведении репозитория в порядок 25.09.2026:

| Файл | Размер |
|---|---|
| `~/backups/pii-proxy-full-<штамп>.bundle` | полная история всех ветвей |
| `~/backups/pii-proxy-worktree-<штамп>.tar.gz` | рабочее дерево без истории |

Бандл проверен (`git bundle verify`, `git clone` из него даёт 177 коммитов). Рабочий снимок —
архив дерева без `.git`. Оба файла **не удалять**: в них остались и прежняя история, и документы
разработки.

Восстановление службы из бэкапа: остановить юнит, положить на место файлы состояния и ключи,
запустить юнит, проверить `healthz` и одну пробную операцию без ПД. Восстановление репозитория из
бандла — `git clone ~/backups/pii-proxy-full-<штамп>.bundle <каталог>`.

## 12. Что делать при отказе службы

1. **`is-active` показывает `activating` или служба циклится.** После нескольких быстрых падений
   юнит упирается в лимит стартов — сначала `systemctl --user reset-failed pii-proxy`, затем
   `status --lines=15` (счётчик перезапусков) и `journalctl -n 30` (настоящая причина).
2. **Служба не поднимается после правки кода.** Правку проверяет статический тест символов точки
   входа (`tests/test_router_startup_symbols.py`), но приёмка — живой старт. Смотреть трассу в
   журнале, а не только состояние юнита.
3. **`healthz` отвечает `degraded` или `store_error`.** Проверить права и наличие файла справочника
   и ключей (0600, владелец — пользователь службы), целостность файла, свободное место.
4. **Запросы возвращают `403`.** Это работа защиты, а не сбой канала. Текст ошибки — по-русски,
   причина — машинным кодом в журнале инцидентов. Частые причины: справочник недоступен, вхождение
   ПД не удалось дотокенизировать, исчерпаны коды, изображение при политике `block`.
5. **Появились алерты/записи инцидентов.** Разбирать по классу и правилу-источнику; повторяющийся
   промах — повод для пополнения словаря (раздел 6) или правки детектора с тестом на оба класса:
   «что обязано находиться» и «что обязано остаться нетронутым».
6. **Ключ или файл справочника потерян.** Коды, выданные прежними ключами, не разрешаются —
   прокси честно откажет (`403`), а не выдумает значения. Лечится только восстановлением ключей из
   бэкапа; создание новых ключей = новые коды с этого момента.

## 13. Переключение агента на прокси и откат

Переключение — **отдельный согласованный шаг**, а не побочный эффект правки: оно меняет работу
живого шлюза. Делается двумя правками и обе откатываются вместе:

1. в профиле агента `model.base_url` → `http://localhost:8791/ds/v1`;
2. ключ поставщика в профиле агента заменяется заглушкой (настоящий ключ остаётся в файле
   окружения прокси, `0600`).

Для сторонних клиентов (Claude Code, Codex, VS Code и расширений) те же две правки делаются в их
настройках — где именно, сказано в разделе 5.1.

Перед правкой — бэкапы обоих файлов со штампом времени. Проверка после переключения — свежая сессия
отвечает **и** в журнале прокси есть новые события. Откат — вернуть `base_url` и ключ; признак
успеха — свежая сессия отвечает, а в журнале прокси **ноль новых событий**.

## 14. Память, лимиты и что отложено

- Целевой RSS основного конвейера — до 150 МБ; `MemoryHigh=200M` работает как мягкий тормоз,
  `MemoryMax=400M` — жёсткий потолок с запасом на морфологию (~17 МБ словарей). Хост на 2 ГБ, поэтому
  тяжёлые стеки (torch) сюда не помещаются: NER подключается лениво и умеет быть выключенным.
- **Firewall-запрет прямого выхода агента к поставщикам — отложен** до отдельного решения оператора:
  пока он не включён, технически возможен обход прокси.
- **Режим заслона связности** переключается `PII_PROXY_COHERENCE_MODE`: наблюдение в `audit` перед
  переводом в `enforce` — решение оператора, а не следствие зелёных тестов.
