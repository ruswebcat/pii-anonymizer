# Как устроен прокси обезличивания

Документ отвечает на вопрос «как это работает и почему сделано именно так». Эксплуатация
(юнит, файлы состояния, правка справочника, восстановление) — в `docs/OPERATIONS.md`;
правовая рамка — в `docs/PRIVACY.md`.

## 1. Место в контуре

```
Пользователь ──► доверенный канал (внутри контура) / внешний мессенджер
                        │
                 агент (хост контура)
                   ├── инструменты: терминал, файлы, код → CRM API (РФ)
                   └── трафик к моделям ──► ПРОКСИ (loopback, порт 8791)
                                              ├── /ds/…   → поставщик 1 (текстовые модели)
                                              ├── /nord/… → поставщик 2 (изображения, медиа)
                                              ├── на входе:  токенизация + заслон
                                              └── на выходе: детокенизация по каналу
```

Агент не знает ключей поставщиков: они живут в файле окружения прокси, а агенту выдан
заглушечный ключ. Прокси — единственная точка выхода трафика к моделям. Слушает только
локальный интерфейс: конфигурация отказывается стартовать при не-loopback адресе.

## 2. Путь запроса

1. **Чтение конфигурации** (`src/config.py`, `M-CONFIG`). Пока не всё проверено, служба не
   поднимается: отсутствующий ключ поставщика, не-HTTPS маршрут, ключевой файл, читаемый группой
   или всеми, не-loopback адрес — отказ на старте, а не «потом разберёмся».
2. **Разбор пути** (`src/router.py`, `M-ROUTER`). Первый сегмент — маршрут (`ds`, `nord`),
   остаток — путь у поставщика. Неизвестный маршрут — `404` и запись в журнал.
3. **Опознание клиента** (`src/client_identity.py`, `M-CLIENT-IDENTITY`). Кто прислал запрос и,
   значит, на каком канале восстанавливать значения. Источники по порядку: заголовок
   `X-PII-Channel` (прежний `X-Hermes-Channel`), отпечаток ключа доступа
   (`X-PII-Client-Key`), шаблон User-Agent из настройки `trusted_clients`, и только затем метка
   доставки внутри запроса (путь Hermes). Не опознан ни один — решение принимает настройка
   `unknown_client` (умолчание — коды остаются кодами). Подробно — раздел 5.
4. **Токенизация всего запроса** (`src/tokenizer.py`, `M-TOKENIZER`). Обходятся системный текст,
   все сообщения, результаты инструментов и аргументы `tool_calls`. Каждое найденное значение
   заменяется кодом, связка «код ↔ значение» уходит в зашифрованный справочник. Опознание клиента
   в обезличивании не участвует: в модель уходят только коды при любом опознании.
5. **Заслон остаточных ПД** (`src/validator.py`, `M-VALIDATOR`). Независимая проверка исходящего
   текста: заслон ищет значения словаря и данные по формату. Проверяется **вхождение, найденное в
   исходном тексте, — оно обязано быть заменено в исходящем**; определения инструментов из
   сканирования исключены, иначе имена параметров вида `image_url` блокировали бы каждый запрос.
6. **Починка вместо отказа** (деградация). Если заслон нашёл остаток, второй проход токенизирует
   его тем же генератором кодов и проверка повторяется уже по починенному тексту. Запрос доходит
   до пользователя, а факт (класс, правило, канал, счётчики — без значений) оседает в журнале
   инцидентов. **Fail-closed остаётся только там, где починка не удалась** — сбой справочника,
   исчерпание кодов, вхождение не найдено, повторная проверка снова грязная: тогда `403` с русским
   текстом ошибки и машинным кодом причины.
7. **Вызов поставщика** (`src/upstream.py`, `M-UPSTREAM`). Непотоковый обмен (JSON) и потоковый
   (SSE). Режим задаётся настройкой: `auto` (как просит клиент) или `json_only` — на случай
   клиента или модели, которые потока не умеют.
8. **Детокенизация на выходе** (`src/detokenizer.py`, `M-DETOKENIZER`,
   `src/stream_relay.py`, `M-STREAM-RELAY`). Восстановление идёт **по клиенту и по каналу**:
   аргументы инструментов восстанавливаются всегда (иначе агент не сможет искать в CRM), текст
   ответа — по настройке `detok_channels`: явный список доверенных каналов либо признак «любой
   канал» (умолчание публичной сборки). Каналы вне контура не восстанавливаются ни при каком
   значении настройки, а клиент, не опознанный ничем, получает решение настройки `unknown_client`.
   Поток чинится кадр за кадром тем же правилом.
9. **Журнал** (`src/audit.py`, `M-AUDIT`). Класс, действие, счётчики, факт попадания в кэш —
   без значений и без ключей.

## 3. Что и как распознаётся

| Класс | Код | Как ищется |
|---|---|---|
| ФИО | `P` | словарь + морфология + правила словообразования, включая латиницу |
| Телефон | `T` | формат в семи формах записи, плюс ключи JSON (`phone`, `contact` вместе с видом контакта) |
| Почта | `E` | формат адреса |
| Дата рождения | `D` | день и месяц; год остаётся открытым — решение оператора |
| Адрес | `A` | формат адреса и контекст «адрес/прописан» |
| Номер карты клиента | `C` | номера карт и клиентские идентификаторы по ключам JSON |
| Документы | `I` | СНИЛС, паспорт, ИНН с проверкой контрольных сумм (ИНН — по двум цифрам ФНС) |

**Три слоя распознавания имён, чтобы не зависеть от одной выгрузки:**

- **A. Открытый слой** — фамилии, имена и отчества из двух независимых открытых проектов
  (`datacoon/russiannames`, списки `natasha/natasha`), живой слой 410 370 значений. Значений
  клиентов здесь нет вообще; ссылка на источник, лицензия и контрольная сумма каждого файла
  записаны в сам файл слоя, сборка воспроизводится одной командой. Лицензионная оговорка — в
  `README.md`.
- **A2. Правила транслитерации** — латинская запись проверяется своими кириллическими вариантами
  против списков. Значения не хранятся, работают правила.
- **B. Частный словарь карточек** — значения из базы системы учёта клиентов в виде ключевых
  отпечатков: файл без ключа бесполезен, читаемых значений в нём нет. Служебные слова, мусор и
  собственная лексика оператора отсеяны стоп-листом.

Плюс морфология (`pymorphy3`) и правило **клиентского контекста**: рядом с признаками работы с
данными (ФИО, телефон, выгрузка, таблица, разделители, длинные числа) значение заменяется даже в
непривычной записи, а в обычном тексте проза остаётся целой.

**Своя лексика оператора — в настройках, а не в коде.** Бренд, названия филиалов и тарифов,
город, свои адреса и телефоны ресепции законно попадают в словарь клиентов: часть карточек заведена
с адресом или телефоном клуба. Они перечисляются в настройках (`M-OWN-VOCABULARY`,
`config.example.yaml`) и никогда не заменяются; в коде публичной сборки своей лексики нет, поэтому
другой оператор получает работающий контур сразу после заполнения примера. Заслон проверяется
одной точкой (`is_own_lexicon_word`), общей для детектора, правил и выгрузки словаря, — иначе они
разошлись бы в оценке того, что считать именем, и запрос блокировался бы на собственной находке.

**Служебная лексика оператора — тоже в настройках** (`M-SERVICE-LEXICON`, раздел `service_lexicon`):
тарифы, названия клубов и услуг, которые система учёта оставляет в поле ФИО. Это данные для
**замера**, а не стоп-лист: измеритель `tools/dict_noise_report.py` (`M-DICT-HYGIENE`) считает,
сколько таких слов лежит в справочнике как «имена», и по решению оператора снимает их оттуда.
Клубно-тарифных слов в коде публичной сборки нет: у другой сети тарифы называются иначе. Общие
категории (должности, статусы, поля системы учёта, заглушки, обрывки) остались в коде — они не
привязаны к конкретной сети.

**Три ключа, а не один.** Код значения считается на ключе токенизации; отпечатки словаря — на
отдельном ключе; справочник соответствия шифруется третьим (Fernet). Если бы словарь считался на
ключе токенизации, любой, кто держит файл словаря, мог бы вычислить код известного клиента и найти
его в запросе — то есть получил бы инструмент связывания. Это зафиксировано тестом.

## 4. Формат кода и почему он детерминированный

Код имеет вид `z` + буква класса + восемь знаков base32 (40 бит), без обрамления. Прежние
поверхности (`[[P-XXXXXXXXXXXX]]`, экзотические скобки) продолжают распознаваться, поэтому старые
связки не ломаются.

- **Детерминированность — не украшение, а условие приёмки.** Одинаковое значение всегда даёт
  одинаковый код, поэтому байтовый префикс уже отправленных ходов не меняется и **кэш поставщика
  модели продолжает работать**. Проверка префикса — прибор `tools/cache_prefix_check.py`
  (сравнение по каждому сообщению, а не по всему массиву).
- **Цена кода измерена.** Обрамлённый 12-значный код стоил на ~58% больше токенов, чем само
  значение, компактный — около +11% (`tools/token_cost_report.py`). Компромисс «коротко и без
  обрамления» выбран по замеру.
- **Достаточность метода считается, а не декларируется.** Регулятор задаёт метод (введение
  идентификаторов со справочником соответствия), но не длину кода. Арифметику ведёт
  `tools/identifier_sufficiency.py`: при 40 битах вероятность коллизии ≈1% на 150 тысячах значений,
  вероятность случайного попадания 1,4·10⁻⁷. Длину страхуют два механизма, а не «побольше знаков»:
  детерминированный обход занятых кодов (то же значение всегда попадает на тот же свободный код,
  значит кэш не страдает) и **восстановление только тех кодов, которые были в запросе** — чтобы
  придуманный моделью код не мог подставить данные другого клиента.

## 5. Граница доверия

**Кто такой «доверенный канал».** Это получатель внутри контура оператора — тот, кому оператор
сознательно разрешил видеть настоящие значения: чат своей команды, терминал агента, локальный
файл, десктопное приложение. Доверенность даёт оператор, а не клиент: служба не выясняет «хороший
ли это клиент», она сопоставляет запрос со **своей** таблицей (`trusted_clients`), а что не
сопоставилось — не получает значений.

| Куда уходит | Что видит получатель | Восстановление значений |
|---|---|---|
| Канал вне контура (внешний мессенджер) | текст с кодами, агрегаты и служебные сведения | **запрещено всегда** |
| Доверенный канал (внутри контура) | текст с кодами | разрешено |
| Любой канал (умолчание публичной сборки) | текст с кодами | разрешено, кроме каналов вне контура |
| Локальные файлы и терминал агента | текст с кодами | разрешено |
| Клиент, не назвавший себя ничем | текст с кодами | **запрещено** (умолчание `unknown_client: keep_codes`) |
| Аргументы инструментов | коды | **всегда** восстанавливаются |
| Поставщик модели | только коды, ни одного значения | не восстановится: ключа нет |

**Чем клиент себя называет и чему это верит.** Порядок источников — он же порядок доверия:

| Источник | Как задаётся | Подделывается |
|---|---|---|
| Заголовок `X-PII-Channel` | `trusted_clients[].header_value` | кем угодно, кто может поставить запрос на прокси |
| Ключ доступа `X-PII-Client-Key` | `trusted_clients[].key_sha256` — **отпечаток**, не ключ | только знанием ключа |
| User-Agent | `trusted_clients[].user_agent` — шаблоны (glob) | кем угодно |
| Метка доставки `[[delivery:…]]` внутри запроса | путь Hermes | кем угодно (системный текст запроса) |

Отсюда честный вывод, который продублирован в `docs/PRIVACY.md`: заголовок, User-Agent и метка
доставки **не являются границей безопасности** — они лишь называют канал, а называть себя можно
как угодно. Границей безопасности служат два других обстоятельства: ключ на клиента (его нельзя
предъявить, не зная) и то, что служба слушает **только loopback** — запрос может подать лишь тот,
у кого уже есть доступ на хост оператора. Поэтому «доверенный клиент» — это запись в настройках
оператора, а не свойство приложения, и поэтому же пустая таблица ничего не разрешает, а
неопознанный клиент по умолчанию получает коды.

Ни один источник не расширяет список каналов: канал, даже названный заголовком, обязан быть
разрешён настройкой `detok_channels`, а каналы вне контура отвергаются на старте
(`CONFIG_CHANNEL_POLICY_VIOLATION`) или в таблице клиентов (`CLIENT_IDENTITY_BLOCKED_CHANNEL`).

Список каналов детокенизации — настройка (`detok_channels`, `PII_PROXY_DETOK_CHANNELS`). Умолчание
публичной сборки — **любой канал** (пустое значение или `*`): обобщённый продукт не знает имён
каналов своего оператора, поэтому значение по умолчанию выбрано владельцем 25.09.2026. Оператору,
которому приватность важнее удобства, список следует **сузить** до своих каналов (см.
`docs/PRIVACY.md`, раздел 3). Каналы вне контура (`telegram` и другие внешние мессенджеры) в нём
отвергаются на старте (`CONFIG_CHANNEL_POLICY_VIOLATION`): выключить защиту неверной строкой в файле
окружения нельзя.

**Неопознанный клиент** (настройка `unknown_client`, умолчание `keep_codes`). Клиент, который не
назвал себя ни заголовком, ни ключом, ни User-Agent, ни меткой доставки, значений не получает.
Настройка `restore` возвращает прежнее поведение — решение по списку каналов; она нужна тому, кто
сознательно оставил восстановление для неопознанных запросов, и ставится явной строкой в
настройках. Правило живёт в той же политике (`ChannelPolicy.decide_for_client`), что и список
каналов: второго места принятия решения о восстановлении в службе нет.

**Изображения.** Скриншоты и сканы обезличить нельзя (нет надёжного способа убрать из них данные).
Политика по умолчанию — пропустить запрос и добавить в ответ напоминание, что изображения с ПД
нарушают политику. Политика `block` (отказ `403`) осталась как явный строгий режим: прежний
безусловный запрет был ошибкой — одна картинка в истории делала нерабочими все последующие запросы
сессии, а vision-маршрут не мог работать вовсе.

## 6. Реестр: «код значит ровно одно значение»

Справочник соответствия (`src/map_store.py`, `M-MAP-STORE`) — локальная зашифрованная база
«код ↔ значение». Инвариант: один код всегда означает одно значение и одного человека. При старте
служба проверяет инвариант; при нарушении (ручная правка файла, слияние копий) **служба
отказывается работать**, а при восстановлении неоднозначный код не подставляется — он остаётся
кодом, и факт пишется в журнал инцидентов без значений. Срок жизни связи — TTL 90 дней.

## 7. Связность персоны: почему доверенная граница проверяет сочетания

Код выдаётся на **значение**, а не на человека: «Ангелина» — один код, «Тестовцева» — другой.
Модель, которой видны коды многих людей, может написать в ответе код не того человека, и
доверенная граница честно восстановит чужое значение: код был в запросе. Так появляется персона,
которой в базе нет — реестр при этом исправен.

Лечит это не длина кода, а связность: сочетание (фамилия + имя, а для полного ФИО — тройка) должно
быть подтверждено источником — карточкой клиента. Индекс сочетаний (`src/name_coherence.py`,
`M-NAME-COHERENCE`) строится инструментом `tools/build_name_combos.py` и хранит **только ключевые
отпечатки**; порядок частей не важен, потому что в карточках поля бывают перепутаны местами.
Снимок индекса на 25.09.2026: 109 711 сочетаний по 49 643 карточкам. Режимы: `off`, `audit`
(считать и записывать инцидент), `enforce` (не восстанавливать сочетание). Если индекс настроен,
по умолчанию действует `enforce` — выдуманный человек хуже пустого места.

## 8. Метрики и планки прибора

Качество обезличивания меряется кодом на фиксированном синтетическом наборе (≥300 значений) и на
чистом рабочем тексте; прибор — `tools/quality_metrics.py`, планки проверяет тест
`tests/test_metrics_guard_planks.py`. Судья любой правки — **доля фактически заменённых данных
клиента**, а не число удалённых строк словаря: чистка, выглядевшая успехом (−21% в классе имён),
уронила обезличение с 99,9% до 73%.

| Метрика | Как считаем | Планка |
|---|---|---|
| Полнота обезличивания значений клиента | доля заменённых на фиксированном наборе | ≥ 95% |
| RepRate | доля незаменённых вхождений с учётом всех форм значения | ≥ 0,95 |
| PhCons | один код на значение во всех вхождениях | ровно 1,0 |
| Ложные замены и ложные блокировки | на корпусе обычного рабочего текста | 0 |
| Обратимость и k-анонимность | успешные восстановления без ключа; доля агрегатов с k < 5 | 0 успехов; k ≥ 5 |
| Доля инцидентов | доля запросов, где заслон нашёл остаток после токенизации, в разбивке по классам | 0 |

Прибор умеет мерить и боевой контур (`--dict-file` с настоящим хешированным справочником и его
ключом), при этом **контур называется рядом с каждой цифрой**: на образцовом наборе планки держатся
иначе, чем на реальном файле словаря.

Метрики «доля инцидентов» нет ни в одном прецеденте: она измеряет не качество на наборе, а
поведение на живом трафике. Планка 0 достигается не прибором, а пополнением словаря — этим
занимается недельный тренер (раздел 10).

## 9. Справочник и его чистка

Правка справочника идёт **одним путём** (`src/dict_write.py`, `M-DICT-WRITE`) — и чистка, и
пополнение тренером пользуются им: собрать staged-файл → прогнать прибор → сделать бэкап живого →
заменить атомарно (права 0600). Порядок обязателен: чистка 17.09.2026 выбросила 12,9% настоящих
значений именно потому, что её никто не измерил перед заменой. Словарь подхватывается на первом же
запросе (в журнале аудита видно `dictionary_reload`), ручного перезапуска не нужно.

Правило чистки опирается на тот же предикат, что рантайм, и отбрасывает только доказуемо
служебное: короче трёх букв или цифр, технические знаки, время суток, ведущая цифра, обычное слово
по морфологии. Стоп-лист своей лексики существует в двух наборах: служебное слово карточки
(«Тест», «Гость») отбрасывается только целиком, а бренд и названия клубов — и как слово внутри
значения. Иначе настоящее ФИО вида «Тестов Тест Тестович» перестало бы обезличиваться.

## 10. Недельный тренер словаря

`tools/incident_trainer.py` (`M-INCIDENT-TRAINER`) раз в неделю читает журнал инцидентов, отбирает
промахи детектора, подтверждает их морфологией и локальной NER-моделью и готовит **пополнение
справочника** через тот же путь записи. Принципы: ни одной языковой модели (нет расхода токенов и
нет ПД наружу), жёсткий недельный лимит добавки, отчёт — цифрами оператору. Расписание —
в `docs/OPERATIONS.md`.

## 12. Соглашения кода

- **Разметка внутри кода — часть кода.** `MODULE_CONTRACT`, `MODULE_MAP`, `CHANGE_SUMMARY`,
  `START_CONTRACT:` и `START_BLOCK_*` держат контракт модуля и его смысловые блоки; тесты и читатель
  на них ссылаются. Парность проверяет `tools/grace_lint_lite.py` (без внешних зависимостей — CLI
  методологии требует `bun`, которого на хосте нет).
- **Только заглушки в тестах, документах и скриптах.** Правило проверяется машиной:
  `tests/test_no_real_pii_in_repo.py` сканирует дерево и требует, чтобы телефон и почта были
  заглушечного вида — по структуре (доля нулей в номере) или по явному списку с причиной у каждого
  значения. Сторож умеет краснеть: положительный контроль собирает незаглушечное значение в
  рантайме и требует, чтобы сканер его нашёл.
- **Секретов и значений ПД в журналах нет.** Журнал аудита и журнал инцидентов хранят классы,
  счётчики, действия и машинные коды — ни текстов запросов, ни значений, ни их фрагментов, ни
  хешей значений, ни путей и ключей.
- **Никаких сторонних зависимостей, кроме уже установленных** (`cryptography`, `pymorphy3`).
  Сеть в тестах не используется: loopback-серверы поднимаются на порту 0.
- **Точка входа проверяется статически и живым стартом.** Отдельный тест разбирает `src/router.py`
  и требует, чтобы каждое глобальное имя, которое читает функция верхнего уровня, существовало:
  полный набор тестов не запускает точку входа, и удалённая функция однажды прошла проверки, но
  служба не поднялась.
